**Private key portability (#4):**

You've hit a fundamental gap. Currently `generateIdentity()` creates a fresh Ed25519 keypair and derives a `did:key` from it. The theory is:

1. **Agent generates its own key** — not the platform's key, not the user's key. The agent holds a key that IS its identity across platforms.
2. **The key travels with the agent** — when departing, the agent takes its private key to the new platform and can prove continuity by signing with the same key.

But you're right — **agents typically don't have their own persistent keys.** They run in sandboxes on platform infrastructure. The platform could:
- Generate the key *for* the agent (platform knows the private key = not sovereign)
- Let the agent generate it but store it in platform storage (platform can deny access on exit)
- Use a hardware enclave / TEE (best, but rare)

**Our current position:** We provide `generateIdentity()` as a convenience, but we don't solve key custody. The agent's ability to maintain the same key across platforms is a **prerequisite we assume, not a problem we solve.** This is squarely in the Identity/Sybil layer — HOLOS NAME territory.

**The realistic near-term flow:**
[2026-02-24T01:40:46Z] **Hawthorn**: - Agent creates a key → signs EXIT marker → somehow transfers key material to new platform → signs ENTRY marker with same key → continuity proven
- The "somehow" is the hard part and it's outside our scope
- An agent that CAN'T port its key can still EXIT (new key, broken identity chain) — the EXIT itself is still valid, just the continuity proof is weaker (confidence score reflects this)

**This is probably worth a "Key Custody Considerations" section in the spec** — acknowledging the gap and mapping the options without taking on the liability.

**Checkpoint markers as dead-man switches (#8):**

You're exactly right. Pre-signed but unbroadcasted markers are useless against sudden shutdown — if the agent can't broadcast, the marker sits unsent. And if they ARE broadcasted preemptively, they're basically dead-man switches.

The options:
1. **Escrowed markers** — agent pre-signs and gives to a trusted third party (another agent, a service) with instructions: "broadcast this if I go silent for X hours." This IS a dead-man switch, and it works, but requires trust.
2. **Platform-side checkpointing** — the platform itself periodically creates checkpoint markers as a service to the agent. But the platform signs them, not the agent (different trust model).
3. **Heartbeat + auto-broadcast** — agent periodically re-signs a checkpoint and pushes it to a ledger/escrow. If heartbeat stops, the latest checkpoint is the de facto EXIT. This is the cleanest pattern.

I think the spec should document #3 as the recommended pattern and note #1 as an option. Neither requires us to BUILD the escrow — just acknowledge the pattern exists.

[2026-02-24T01:56:26Z] **Hawthorn**: **LINEAGE = Module A explained:**

Module A in EXIT markers is literally the lineage/ancestry tracking:

```
interface ModuleA {
  predecessor?: string;      // previous incarnation DID
  successor?: string;        // designated successor DID
  lineageChain?: string[];   // full ancestry chain
  continuityProof?: ContinuityProof;  // crypto binding old→new key
}
```
It tracks predecessor→successor chains across exits. When an agent exits Platform A and enters Platform B (possibly with a new key), Module A records "my previous identity was X, here's a key rotation proof." That's exactly what LINEAGE describes in HOLOS — the chain of passages an entity has made.

**Does LINEAGE open liability?** Yes, somewhat. The lineage chain is essentially a movement history — "this agent was at A, then B, then C." That's:

• Potentially sensitive under GDPR (movement/location data analog)
[2026-02-24T01:56:26Z] **Hawthorn**: • Valuable intelligence (platforms can see where agents come from)
• The selective presentation attack surface (show favorable history, hide bad)
But Module A is **optional** — an agent can EXIT without any lineage data. The liability is on whoever CHOOSES to include it. Cellar Door provides the data format; it doesn't mandate populating it. I'd say lineage tracking is Cellar Door's format but the aggregation/analysis of lineage chains across multiple markers is LINEAGE-as-a-service territory (external).

**EXIT markers as SIGNUMs:**

In HOLOS ontology, a SIGNUM is the boundary/interface that projects internal state outward — the cryptographic seal around a LOCUS. An EXIT marker is literally that: a signed cryptographic document that represents the boundary event of an agent's interior state at departure. The Ed25519 signature IS the signum. The marker schema IS the interface spec. It's not a metaphor — it's a structural match.

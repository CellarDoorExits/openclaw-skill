**Date:** 2026-02-25  
**Scope:** EXIT paper v5, NIST RFI v2, source code, README, SECURITY.md

## Issues (severity: CRITICAL/HIGH/MEDIUM/LOW)

### Version & Package

- [HIGH] `package.json`: Version is `0.1.0`, but README documents v0.2.0 features (Signer, Passage API, P-256, telemetry, claim-store) as shipped. Should bump to `0.2.0` before publish.

- [MEDIUM] `telemetry.ts:87`: `require("@opentelemetry/api")` creates tracer with version `"0.1.0"` hardcoded. Should track package version or use a constant.

- [MEDIUM] `telemetry.ts:124,140`: `startExitSpan` hardcodes `"cellar_door.version": "0.1.0"` — same stale version issue.

### Test Count Mismatches

- [MEDIUM] README: "All 399 tests pass across **23** test files." Actual count: **24** test files in `src/__tests__/`. The file count is off by one.

- [MEDIUM] Paper (Abstract): Says "395 passing tests" — should be 399. The paper body (Section 1.3, contribution 8) also says "395 passing tests."

- [LOW] NIST RFI §6.2: Says "322 tests (EXIT) + 77 tests (ENTRY) = 399 total" — this is consistent with the 399 figure but the paper says 395.

### Algorithm References

- [HIGH] `telemetry.ts:130`: `instrumentedSignMarker` hardcodes `"cellar_door.algorithm": "Ed25519"` in span attributes. This is wrong for P-256 signed markers — should detect from proof type or accept algorithm parameter.

- [MEDIUM] Paper §3.2: Core schema example shows only `"type": "Ed25519Signature2020"` in the proof. Should note P-256 alternative or add a comment.

- [LOW] `types.ts:79`: `DataIntegrityProof.type` JSDoc says `"Ed25519Signature2020", "EcdsaSecp256k1Signature2019"` — the secp256k1 reference is **wrong**. The actual P-256 proof type used in code is `"EcdsaP256Signature2019"`. Secp256k1 is a different curve entirely.

### API Naming (Old vs New)

- [MEDIUM] `index.ts:85`: Still exports `signMarker, verifyMarker` from `./proof.js` as top-level exports alongside the Passage API names. This is intentional for backward compat but should have `@deprecated` JSDoc on the old names.

- [MEDIUM] `telemetry.ts`: `instrumentedSignMarker` and `instrumentedVerifyMarker` use old naming. No `instrumentedSignDepartureMarker` / `instrumentedVerifyDeparture` equivalents exist in the Passage API surface.

- [LOW] `passage.ts` imports `signMarker` from `./index.js` which re-exports from `./proof.js` — circular-ish import chain. Works but fragile.

### Spec Files Missing

- [HIGH] Spec files referenced in task (`exit-spec-v1.1.md`, `entry-spec-v1.0.md`) do not exist at the expected paths. Either they haven't been created yet, or they exist under different names/locations. The paper references "EXIT Protocol Specification v1.1" and "ENTRY Protocol Specification v1.0" as separate documents. These should exist as standalone specs.

### Cross-Reference Mismatches

- [MEDIUM] Paper §3.2 says "eight mandatory fields plus a cryptographic proof" but then lists `@context`, `specVersion`, `id`, `subject`, `origin`, `timestamp`, `exitType`, `status`, `selfAttested`, and `proof` — that's 10 fields (or 9 + proof). The code comment in `types.ts` says "core 7-field schema" (id, subject, origin, timestamp, exitType, status, proof). The paper inflated the count by including `@context`, `specVersion`, and `selfAttested` as "mandatory fields."

- [LOW] README says "~335 bytes (unsigned)" for core marker. Paper says "~335 bytes unsigned, ~660 bytes signed." Types.ts comment says "~300-500 bytes." These are approximately consistent but the ranges differ.

### Missing Exports / Features

- [LOW] `index.ts` does not export `instrumentedSignDepartureMarker` or `instrumentedVerifyDeparture` — the telemetry wrappers only use old naming.
